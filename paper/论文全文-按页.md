2 Background and Related Work

2.1 Scan Semantics and PLC Verification

A cyclic PLC task invokes its program at a configured interval [11]. Each scan reads inputs, executes
the control program, and updates outputs. ST statements follow the program’s control flow, so
assignment order can affect later statements in the same scan. ST organizes code into program
organization units (POUs): functions, function blocks, and programs. Their interfaces declare inputs
(VAR_INPUT), outputs (VAR_OUTPUT), and read/write arguments (VAR_IN_OUT, or inouts). Function-
block instances retain internal state across calls [15, 39]; timer blocks also depend on elapsed
time [5]. Thus, behavioral testing must fix the input sequence, initialization, time progression, and
observed scans.

   PLC verification provides several forms of evidence. STbmc performs bounded temporal-property
checking [25]; SymPLC explores paths and task interleavings symbolically [14]; K-ST gives exe-
cutable ST semantics and validates implementations differentially [39]; and PLC simulation can
step through scan cycles [34]. These techniques analyze a given program against properties or
formal semantics. Comparing generators also requires a shared task suite with expected behavior,
which CycleBench provides.

2.2 LLM Generation, Testing, and Repair

General-purpose benchmarks evaluate function synthesis [7], library use [44], contest problems [16],
and repository changes [18]. EvalPlus expands test coverage [27], and DPIaC-Eval tests infrastruc-
ture code for deployability [43]. Reference-based execution also appears in other code domains:
VerilogEval compares simulated hardware outputs with golden designs [28], and SolBench uses
differential fuzzing against original smart-contract functions [10]. CycleBench applies reference
comparison to PLC scan execution under controlled initialization and logical time, and RQ4 isolates
the effect of which scans are observed.

   Execution feedback can also guide generation. CodeT selects among candidates using generated
tests [6], Self-Debugging feeds execution results into repair [8], and MBR-EXEC and DOCE study
execution-based selection and refinement [26, 35]. Generated expectations and self-repairs can
themselves be wrong [9, 30]. This motivates measuring selection and repair separately from the
reference-based final verdict.

2.3 LLM-Based PLC Methods

Early studies examine direct generation of PLC control logic [23, 37]. Later approaches add retrieval,
specialized training, or structured control representations [13, 22, 24, 33]. PLC test generation and
mutation datasets provide further ways to examine test quality [19, 21].

   The closest workflows combine generation with feedback. LLM4PLC uses user-guided iteration
with grammar, compiler, and SMV checks [12]. Agents4PLC integrates retrieval, planning, coding,
debugging, and validation agents with formal specifications [29]. AutoPLC retrieves vendor-specific
cases and APIs and uses vendor-toolchain diagnostics for repair [40]. SemaPLC combines project
or interface context with specification, compilation, and runtime checks; its native verification gate
controls delivery [38]. Its runtime strategy combines sampled traces with persistent assertions.

3 Benchmark: CycleBench

Under PLC scan semantics (Section 2.1), program outputs can depend on input history, retained
state, and timing. Successful compilation or agreement at selected scans can therefore leave interme-
diate behavioral errors undetected. To assess generated ST programs under a common behavioral
criterion, we construct CycleBench. Its core idea is to pair reviewed public specifications with
reference programs and input scenarios, and compare candidate and reference outputs after every
scan under aligned inputs, public initialization, and logical time. CycleBench contains 301 ST
function blocks and programs, with references and evaluation scenarios hidden from generation.
This protocol exposes output discrepancies within the supplied scenarios.

4.1 Candidate and Test Generation

CycleGen receives the behavioral requirement, public interface, initial values, and ST dialect rules.
The same model authors tests and code in separate contexts. Tests are fixed first and withheld from
code generation; both stages precede candidate execution.

   This ordering makes the suite candidate-blind: test authorship cannot respond to an observed
implementation or its execution results. Withholding the suite also keeps candidate generation from
directly targeting its assertions. However, both contexts use the same model and specification, so a
shared misunderstanding can still appear in code and predicted outputs. Candidate-blind authorship
therefore controls information flow, not semantic independence. Reusing one unchanged suite
makes candidates comparable on the same input histories and assertions; it does not turn model
predictions into a correctness oracle. RQ3 measures the consequences of this distinction through
controlled selection contrasts and a separate self-test diagnostic.
Test generation. Each case specifies a reset, an input sequence, predicted scan outputs, and a
requirement anchor: a model-authored quotation of, or reference to, the public requirement clause
that the case is intended to test. For example, a retention test may cite a clause requiring an output
to remain active after an input is withdrawn. Its scan sequence then activates and withdraws
that input. This annotation describes the intended behavior; it is distinct from the input/output
declarations. Every scored scan specifies all ordinary inputs and expected observable outputs,
including inout members. An explicit inout write overwrites its current value; an omitted write
leaves the current value unchanged. One suite serves the entire pool.

   Before execution, validation checks the test format, declared input/output names and types,

4.2 Compiler-Guided Repair

Compile-Fix uses Matiec’s iec2c front end to translate ST to C. Each nonempty candidate that
fails this check receives at most one repair request containing the public specification, its code,
and front-end diagnostics. A revised POU replaces the original only if it preserves the exact public
interface and passes the same check; otherwise the original candidate and failure status are kept.
A successful repair keeps its sampling slot. A candidate is eligible when it preserves the interface
and passes ST-to-C translation. Interface preservation is checked separately from compilation and
requires the specified POU name and public input/output declarations. This gate does not perform
native GCC compilation or linking. All eligible candidates use the same fixed tests.

4.3 Runtime Self-Testing

Front-end acceptance does not establish executability or correct behavior. Self-Test attempts to
build each eligible program with GCC and run the shared test inputs in the benchmark runtime
(Section 3.2). Build failures yield incomplete self-test execution. Each case starts fresh, retaining
state between scans; inputs precede each scan and logical time advances by its interval. Self-test
uses Python value equality with boolean/numeric normalization; the final evaluator uses recursive
type-and-value equality. A scored case passes only on complete matching execution. Runtime-valid
means every scored and unscored case completes, not that predictions are correct. Only scored
cases contribute pass and mismatched output-field counts; infrastructure faults and incomplete
traces have separate statuses. Wrong predictions can penalize correct or favor incorrect code [9, 21];
RQ3 checks this signal against the hidden oracle.

4.4 Candidate Selection

Following execution-based selection [26, 35], CycleGen ranks eligible programs lexicographically:
complete execution first, more passing scored cases next, then fewer mismatched output-field
assertions. Exact ties are resolved by generation order. In the figure’s example, C3 wins its tie with
C4 because it was generated earlier.

7 Threats to Validity

Construct validity. Execution pass rate measures reference agreement on supplied scenarios,
not full requirement coverage, unseen inputs, physical behavior, or termination. Exact equality
may count numerical rounding differences as failures. Two PLC engineers checked requirements
against sources, interfaces, and available reference behavior. RQ2 assigns one primary label to
each behavioral failure; independent annotation assesses consistency, not unique root causes or
sparse-category accuracy (Section 6.2).
Baseline fidelity. Agents4PLC and LLM4PLC retain compiler-feedback repair but omit described
formal-verification loops; common scoring cannot restore generation-time verification. Results
characterize these adaptations, not native systems. Sampling and inference budgets differ; shared
pools narrow but do not remove this limitation.
Internal validity. Reference self-checks, fresh state, aligned logical time, hidden-data isolation,
and versioned images constrain initialization, timing, and evaluator effects.
External validity. Eight deployments cover 301 tasks; taxonomy and observation analyses cover
five models. Source concentration and limited scenarios constrain diversity and coverage [1]
(Table 2). Baseline-derived tasks and Qwen3-Coder-Next’s roles in scenario authoring and evaluation
may affect results; training exposure remains unknown. Fixed budgets, one runtime, and provider-
specific reasoning limit transfer to other dialects and physical controllers (Section 5). AutoPLC’s
lower compilation under our adapter cannot be attributed to individual components.
Conclusion validity. Task-level paired resampling preserves method–model correlation. The
CycleGen configuration was developed using this benchmark. Independent tasks and repeated gen-
erations are needed to assess generalization and sampling stability. Ablations estimate conditional
effects under the reported controls.

8 Conclusion

CycleBench evaluates LLM-generated ST through scan-by-scan execution on 301 PLC tasks. Across
eight models and four baseline methods, execution trails compilation by 11.92 percentage points.
Every-fifth-scan checking misses 21.66% of 157 behavioral failures in the five-model Direct analysis,
even with scenario endpoints retained; transient discrepancies and sampling phase explain these
misses. CycleGen combines multiple candidates, compiler-guided repair, and runtime self-tests,
raising execution pass rate from 74.63% to 83.31%. Controlled-pool ablations support repair and self-
test selection, while increasing the candidate count beyond five adds token cost without improving
execution pass rate. These findings motivate scan-by-scan evaluation and behavioral feedback for
generated PLC programs.
